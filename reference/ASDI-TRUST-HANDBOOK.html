00 · Executive decision

ASDI is a trust control plane for agent-driven delivery.

ASDI does not trust an agent because it is capable, has completed many tasks, or says that its work is done. Trust is established by the environment in which the agent operates and by evidence independently produced and evaluated outside that agent.

Core propositionASDI owns cross-project enforcement and authority. Each product owns the domain knowledge and procedures needed to verify its behaviour. An agent may produce code and evidence candidates; it cannot certify its own success, weaken the acceptance criteria for the change being judged, or authorize its own delivery.
1Human directionAdmit outcomes; retain judgment and irreversible decisions.
2Bounded executionLauncher, run sandbox, budget and credential boundaries.
3Independent proofASDI reruns product proofs and deterministic gates.
4Policy decisionClass, review, evidence freshness and authorization.
5Production feedbackPost-merge verification, canary, rollback and learning.

This joins the five-layer trust model associated with Lauren Tan, pstack's project verification methods, and gstack's explicit handoffs—while making ASDI the independent enforcement authority. The design's C-5 rule is decisive: the agent's claim of success never counts; only ASDI-run verification does.

02 · Trust baseline

Why an agent's own success report is insufficient

What the harness contributes

  • Project-specific architecture and domain context.
  • Static checks and tests that make known failures detectable.
  • Procedures to launch, drive, observe and clean up the real product.
  • Feature-level proofs with explicit limits and negative controls.

What the platform must contribute

  • Clean, isolated verification independent of the agent session.
  • Trusted policy inputs and protected verification paths.
  • Evidence provenance, integrity and freshness.
  • Independent review, class evaluation and delivery authority.

pstack helps define what a meaningful product check looks like; gstack contributes explicit engineering handoffs and shipping discipline. Neither is the trust authority for ASDI. ASDI joins the meaning of the project proof to a trusted execution and enforcement boundary.

Do not confuse three distinct propertiesVerification capability: the project can exercise the behaviour that matters. Verification reliability: the procedure detects the failures it claims to detect. Verification enforcement: ASDI blocks progression unless independent evidence satisfies the gate. A green status is meaningful only when all three are addressed.

Trust is task-relevant, not a global score for an agent. A model may be reliable at documentation edits and unproven at database migrations. A task type earns autonomy only when its own product harness, evidence and historical outcomes justify it.

03 · Ownership boundary

Centralize enforcement semantics; decentralize product knowledge.

Use the ordered test defined in Build Guide V4 §3. ASDI-native ownership is warranted when a failure must be blocked, when authority/credentials/network reach must stay outside the agent, when evidence must be independent of the implementer, or when state must outlive a run or cross trust zones. Knowledge about one product's behaviour belongs in that product's harness. Other guidance is a request.

04 · Conceptual architecture

Six logical modules, not six deployables

The six responsibilities below are a useful way to reason about the trust control plane. The implementation mapping is defined by Build Guide V4 §19. They are not six independently deployed services or six new per-project control planes.

1. Trust Profile Registry

The product profile describes the product, run image, services, task types and architecture baseline. The authoritative T0–T2 ledger lives in ASDI state, not in the product repository.

Guide: `.asdi/product.yaml` + TRM ledger
2. Verification Contract Compiler

Turns an admitted outcome into a validated run contract with objective, rationale, constraints, out-of-scope items and `done_check`. Defaults remain overridable requests unless hard rules apply.

Guide: brief compiler + launcher contract validation
3. Evidence Ledger

Stores content-addressed evidence and run/PR/probe/sweep manifests. Tracks producer, commit, environment, inputs, limits and validity.

Guide: `evidence/` (N-2, N-18)
4. Gate / Policy Evaluator

Combines change class, path coverage, verification outcomes, review verdicts, evidence validity, waivers and fail-closed rules into a delivery decision.

Guide: Archon class check; N-4, N-5, N-19, N-23
5. Review Coordinator

Requests scoped reviews, supplies trusted inputs, enforces independence requirements and records evidence-backed findings and dispositions.

Guide: Archon review passes; N-6 to N-8
6. Trust and Rule Lifecycle

Tracks TRM transitions, recurring corrections, rule promotion/retirement, skill evaluations, seeded defects and verification drift.

Guide: TRM, compounding, evals and seed suite

05 · Five-layer trust model

Diagnose agent failures at the strongest effective layer.

The five layers form a diagnostic ladder. When a human corrects an agent, ask where the failure should be prevented structurally. Do not default to adding another prompt instruction. Each layer addresses a different failure class; skills are not a substitute for static enforcement, and automated review is not a substitute for the ability to verify the actual product.

1 Codebase architecture — make the right path natural

Shape module boundaries, domain types, canonical data paths and interfaces so invalid states and common anti-patterns are difficult to introduce. Keep the architecture legible enough that a model can infer the intended pattern from local context.

Project artifacts: architecture baseline in the product profile, canonical domain models, explicit interfaces and dependency boundaries. ASDI support: coverage gate (N-4), change classification and compounding into a structural correction.

Success criterion: a seeded anti-pattern is prevented or made materially harder by the structure; the fix is not merely written in agent instructions.

2 Static analysis — reject deterministic violations

Use compilers, type checkers, linters, static security analysis and deterministic tests where a rule can be decided mechanically. A check must execute in a clean verifier environment and fail closed on crash, timeout or missing inputs.

Project artifact: H-6 static-gate manifest. ASDI support: N-17 static-gate runner; policy and manifest are read from the trusted base branch, not the candidate PR head.

Success criterion: the original violating change is rejected without relying on a human reviewer to notice it. A PR that changes a gate command to `echo pass`, deletes the manifest or removes a required check is still judged using the base-branch version.

3 Persistent rules — preserve conventions that require judgment

Record conventions that cannot reasonably be enforced mechanically. Keep the project instruction source singular: `AGENTS.md` is authoritative; `CLAUDE.md` is a one-line import of it. Rules that claim to be project-hard must point to a structural, static or test mechanism and a negative test; mere prose is not enforcement.

Project artifacts: `AGENTS.md` and H-7 rule registry. ASDI support: rule classification, protected paths, review deviation handling and N-10/N-11 lifecycle.

Success criterion: agents receive persistent project context; deviations are visible and reasoned; edits to instructions/skills are evaluated rather than merged on persuasive wording alone.

4 Automated review loops — independently audit change and blast radius

Use a reviewer context independent from the implementation agent to challenge the change, its assumptions, security implications and effects outside the diff. Reviewers receive the contract, trusted base/head diff, policy snapshot and verification evidence. A reviewer finding needs a location, consequence and evidence.

ASDI-native: N-6 verdict/findings schema, N-7 blast-radius pass, N-8 security pass, N-9 packet assembly. The full target includes four scoped passes: contract, correctness, security and blast-radius.

Stage distinction: Pass 1 uses one review pass. Pass 2 adds the four-pass model and post-merge deep sampling. Do not claim the full review system exists in Pass 1.

Success criterion: seeded defects that escape lower-layer checks are found by the appropriate independent audit; unavailable independent review blocks or routes to a human, never self-review.

5 Procedural skills — teach agents how to produce product evidence

A skill is an executable project procedure, not simply an instruction to “test thoroughly.” It teaches an agent how to launch, inspect, drive, observe and clean up the real application. Deterministic work belongs in scripts/drivers; model reasoning interprets results and limits.

Project artifacts: H-1 verify skill, H-2 feature map, H-3 negative controls, H-4 fixtures/drivers, and later H-5 read-only production probes. ASDI support: N-1 clean verifier, N-4 coverage gate, N-5 verification-path protection, N-13 drift sweep and evidence validation.

Success criterion: the agent can reproduce a user-visible workflow, compare observed output with a literal expected value, catch a deliberately broken case and leave reproducible evidence. The harness itself must pass its self-test.

Five layers are not five required new servicesThey are five intervention surfaces. Most project-specific mechanisms live in the product repo; ASDI supplies the independent runner, protection and policy that make them trustworthy.
06 · Keep two ladders distinct

The five trust layers are not the same as the four compounding levels.

Build Guide V4 §11.1 defines a four-level correction-placement ladder. It is an implementation procedure for recurring mistakes; it is not a replacement or renumbering of the five trust layers above.

Guide correction levelPreferred fixRelationship to five trust layers
1Change the codebase so the mistake is impossible or unnatural.Trust L1 architecture.
2Add a type, lint or CI check.Trust L2 static analysis.
3Add a behavioural test.Deterministic verification supporting L2; not a separate sixth trust layer.
4Add or change `AGENTS.md` or skill text, with skill evaluation.Trust L3 persistent rules and/or L5 procedural instruction. Use only when higher structural or mechanical fixes are unsuitable.

Trust L4 automated review is a separate audit capability. It is not a fallback step in the correction ladder: reviewers surface defects and evidence that may then trigger a correction at level 1–4. A repeated correction in text at guide level 4 should be escalated if it can be encoded mechanically.

Compounding trigger and disciplineThe same correction appearing twice starts a review; it does not automatically create a hard rule. The compounding mechanism must propose the highest effective fix and explain why stronger layers do not apply. Every fix updates the rule record; guide levels 1–3 add a seed showing that the original mistake is now caught. Text/skill changes require blinded evaluation.
07 · Rule classes and lifecycle

Only hard rules are absolute; conventions remain adaptable.

ASDI distinguishes platform-wide non-negotiable rules from project-level hard invariants, conventions and task-specific constraints. This keeps the platform safe without turning every preference into micromanagement.

Rule classSourceEnforcementCan agent override?
Platform hardDesign doc §02; trusted ASDI configLauncher, identity, network, verifier and policy gate.No.
Project hardProduct `.asdi/rules.yaml`Must be enforced at a structural/static/test level and have a negative test.No, unless an authorized waiver exists under ASDI policy.
Convention`AGENTS.md` and project rule registryReview; deviation requires a reason and is recorded.Yes, with a reason.
Task-specificAdmitted run contractContract review and run verification.Only through the authorized brief/contract process.

The seven platform hard rules

  1. Merge authority by change class. Only the merge identity merges after required checks and policy pass; judgment-class changes require the human. Agent tokens cannot merge.
  2. `done_check` is ASDI-verified. The agent CLI hook is only a convenience; the launcher verifier decides for every CLI.
  3. Sandbox. A container and network per run, egress allowlist, own branch only, and no route to production.
  4. Secrets outside the sandbox. Tokens and model credentials are injected at egress; production secrets exist only on the production network.
  5. Guardrails. Turn, spend and wall-clock limits per run, enforced externally.
  6. No irreversible agent actions. Exposure ramps, shared-data migrations, external side effects, pricing and force-pushes remain human decisions; production migrations require a just-before snapshot.
  7. Protected paths. Generated/vendored code is not edited. Changes to tests, CI, `verify/`, `evals/` or `.asdi/` are flagged; a product PR may add a feature file but cannot alter existing verification files.

Instruction source and override discipline

`AGENTS.md` is the source of truth in every repository, including ASDI. `CLAUDE.md` contains only `@AGENTS.md`; Codex reads `AGENTS.md` directly. An agent may override requests and record why in `OVERRIDES.md`; those explanations are included in the PR packet. A request ignored twice is promoted only if it is genuinely must-always/must-never. Preferences are demoted. Model releases trigger review of the rule set.

Rule lifecycle

  • Record the source, scope, class, enforcement mechanism, owner, negative test, recurrence count and status.
  • Repeated correction → candidate fix at the strongest effective layer → review/classification → implementation PR → evaluate catch rate.
  • Changes to `AGENTS.md`, skills or evals require blinded paired skill evaluation across the CLIs in use: no regression in any case and improvement in the targeted case.
  • Rules with no recurrence across a full model-release cycle become retirement candidates; retain history.
08 · Evidence semantics

Evidence is valid only when its provenance and inputs are trustworthy.

Evidence records what ran, where, with which tool and environment, against which revision and inputs, and what was observed. It does not by itself prove that the chosen test is adequate; the feature map, negative controls, policy and review assess adequacy.

Validity conditions

ConditionRequired propertyWhy it matters
Revision-boundThe evidence subject commit equals the commit the gate is judging.Results from one code revision cannot authorize another.
Producer-boundPass 1: only the trusted launcher/verifier path writes to the evidence store. Pass 2: attestation signature verifies against the verifier identity.An agent's self-authored claim is not an attestation.
Environment-boundRun image digest and tool versions are recorded.Results must be interpretable and reproducible.
Input-boundHarness commit is from the trusted base branch; hashes of static-gate manifest and product profile match.The candidate cannot replace the checks used to judge itself.
Integrity-protectedEach evidence file's SHA-256 matches its stored content-addressed object.Mutation or corruption invalidates the record.
FreshAny new PR head commit invalidates all evidence and review verdicts for that PR in this version; no selective carry-forward.Old proof cannot authorize changed code.
Honest outcomes`pass`, `fail`, `blocked`, `error`, `not_applicable` remain distinct; only `pass` satisfies a gate.Unavailable checks and tool crashes must not become green.
Limits statedEach feature result states what was not covered, even if the list is empty.A bounded proof is more trustworthy than an overstated claim.
Trusted policy rootASDI reads the static-gate manifest and existing verification material from the pinned base branch, never from the candidate head. A PR that changes a gate is judged by the old/base version, and that policy change is itself routed to judgment. This mechanically prevents self-weakening for the current change.

Evidence signing is staged

Pass 1 uses an evidence directory/store with trusted launcher-only writes and content hashes. Pass 2 adds signed in-toto/DSSE attestation. Do not describe signed evidence as a Pass 1 capability. The handbook's trust requirement is provenance and integrity; Build Guide V4 owns the implementation timing and attestation schema.

What the deployer trusts

The baseline is direct merge, not a merge queue. ASDI reruns static gates and product verification on the exact commit that landed on `main`. A failure opens an auto-revert and stops release. Deployment is allowed only for a `main` commit with a passing post-merge result. Evidence is commit-bound; there is no merge-group attestation or tree-bound queue tier in REV K.

09 · Review and delivery authority

Review produces evidence; the policy gate authorizes movement.

Review is narrow, independent and evidence-backed

The full target uses four scoped passes: contract, correctness, security and blast-radius. Each pass returns a verdict and findings categorized as act, consider, noted or dismissed. No evidence, no actionable finding. Reviewer inputs include the brief/contract, trusted base/head diff, policy snapshot and verification evidence—not merely the implementer's narrative.

  • Correctness and security use a different model family from the build agent where available.
  • Reviewers operate in fresh context. The implementer never self-reviews.
  • If a second model family is unavailable, the change routes to judgment; reviewer unavailability blocks or routes to a human.
  • Pass 1 is deliberately thin: one review pass. Pass 2 adds the four-pass system and deep sampling.

Direct merge and post-merge verification

The PR-head gate requires `ci`, `asdi/policy` and an up-to-date branch. The merge identity merges directly; until agent merges are enabled, the human merges. The same static gates and verifier then run on the commit actually on `main`. Failure opens an auto-revert PR and stops release; success makes that commit eligible for image build and deployment. There is no merge queue in REV K. A queue is a future option only if the deferred merge-path decision changes.

Human touchpoints remain deliberate

  1. Admit work within WIP limits.
  2. Decide genuine escalations and irreversible actions.
  3. Review judgment-class PRs.
  4. Gate exposure: preview, ramp, keep or kill.
  5. Run the weekly system loop: metrics, TRM, rule retirement, experiment verdicts and flag debt.
10 · Trust and task maturity

Autonomy is earned per task type, and can be lost.

TRM records the demonstrated reliability of a task type, not a general ranking of an agent or model. The ledger is held in ASDI's database; maturity is never stored in the product repository. Judgment-class paths remain human-controlled at every level.

LevelSupervisionPromotion / demotion
T0 · ProbationHuman agrees key assumptions for structural work and previews feature prototypes. Human merges all work. Pilot batch work; provide a live link for initial runs.Three first-pass approvals → T1, only after harness self-test is green, feature coverage meets threshold and required seeds are caught.
T1 · StandardAgent plans; a staff-review agent checks assumptions and slice overlap; steer agent watches first minute. Merge bot may merge agent-mergeable changes. Deep sample 1 in 5.Five additional first-pass approvals and no reverts for 30 days → T2. Any revert returns the task type to T0.
T2 · TrustedAs T1, with steering sampled. Merge bot for eligible changes. Deep sample 1 in 10.Revert or escaped defect → T0. Two resets in a row → T1. A model release returns it to T1 until the evaluation set passes.

Promotion is a proof obligation

  • The product harness self-test passes.
  • Every product source path is covered by a feature, or the change is classified judgment (documentation exemptions as defined in the guide).
  • No touched feature was blocked in the last three runs.
  • Every seeded defect is caught by its named control before T1.
  • First-pass approvals and revert history meet the thresholds.
Do not promote on volume aloneAgent-merge share, PR count and first-pass rate must be paired with reverts, escaped defects, seeded-defect catch rate, reviewer false positives and evidence freshness. Higher throughput without stronger verification is not higher trust.
11 · Acceptance criteria

Each layer must demonstrate that it catches the failure it claims to prevent.

This handbook defines what constitutes adequate evidence. Build Guide V4 §14 contains the executable phase tests, command targets and exact implementation exit criteria. Do not duplicate or invent a second phase plan here.

Trust layerPositive evidenceNegative / adversarial acceptance
L1 · CodebaseCanonical boundaries and domain constraints are documented and used by the product code.Introduce a known structural anti-pattern; architecture or boundary enforcement prevents it or makes the violation detectable before delivery.
L2 · StaticBase-branch static gates run in a clean verifier and report distinct outcomes.Candidate removes a check, changes a command to pass trivially, times out or crashes the tool; the trusted base check still runs and the gate cannot pass.
L3 · RulesEvery project-hard rule names its enforcement mechanism and negative test; conventions are persistent and deviations are reasoned.Rule/skill edit regresses a blinded evaluation case; the skill-eval gate rejects it. Prose-only rule is not counted as mechanical enforcement.
L4 · ReviewIndependent reviewer returns a scoped verdict with findings, evidence and dispositions tied to the reviewed revision.Seeded defect escapes lower layers; reviewer detects it. Missing reviewer or missing model-family independence blocks or routes to human, never self-review.
L5 · SkillsVerify skill launches, checks health, drives a feature, observes literal output, emits evidence and cleans up.Negative control intentionally breaks a feature; the harness catches it. If its control is missed or evidence is invalid, the harness is unusable and affected product work is judgment-class.

Core invariants to preserve

  • Only `pass` satisfies a gate; `blocked`, `error` and `not_applicable` are not silently coerced to pass.
  • Existing verification files are protected from ordinary product PR edits. A new feature file is permitted only with review of the check itself.
  • Tool crashes/timeouts fail closed. Flaky proof is blocked, not retried until green.
  • Evidence missing, mismatched, stale or unverifiable invalidates the gate.
  • Production probes are read-only, allowlisted and run without a model or write credentials.
