Archon rule: Archon wraps outcomes and pipelines; it never scripts how the build agent works. A build run is one agent task launched by the board (Multica or Paperclip); the agent picks its method and done_check is checked by the agent CLI's own stop hook where it has one, and re-checked for every CLI by the launcher's verifier in a clean container (C-5). Archon is never called from inside an agent (no nested budgets, no agents inside agents), and it never uses interactive approval nodes.

Multica + Archon wins on

  • Native multi-host dispatch: no longer counts on one host; it returns if you add a machine
  • Runtimes auto-detected with a liveness check, no receiver to build
  • Squads with leader agents, matching your architect role without a company structure
  • A Hermes runtime, so local-model workers stay possible

Paperclip + Archon wins on

  • A hard budget stop at 100% (Multica needs caps in the launcher)
  • Heartbeats as built-in scheduled wakeups
  • Board approvals that map onto your exposure gate

Cost: company and governance ceremony to configure away, which is why R6 stays a point lower.

What moved: on one host only R1 changes. Paperclip goes 2 → 3 because its weakness there was an adapter receiver per machine and no multi-host dispatch; Multica stays at 3 because its multi-host strength no longer earns anything. 04Consequences and failure modes

Consequences

  • The Studio is a single point of failure for production and delivery. Recovery means replacement hardware plus an offsite restore.
  • Two Postgres-backed servers (board, Archon), the prod containers and local models share 256 GB. Memory caps per zone and production-first admission are what keep users safe.
  • Every run gets its own container and network from the first build phase. All zones share one Docker daemon and one kernel, so the socket proxy and container hardening carry the isolation.
  • Timers are hourly sweeps, not durable workflows. If a window ever needs minute precision, revisit.
  • Guardrails are enforced by the ASDI launcher from outside the run, whichever board is used. Paperclip also has a native spend stop.
  • Build order is lifecycle first: the thinnest version of every part until a production error comes back as a merged fix, then hardening. The guide §13 has the phases.
  • Up to 60 s latency per GitHub event, which these loops tolerate.

Verify when each part is built

Only the GitHub check runs up front. Timing for the rest is in the guide §13.5.

  • Multica (if kept): task-cancel API for the steer agent; a runtime as a wrapper command for per-run containers and budget caps. Paperclip (if chosen): cancelling a running task through the adapter; adapter receiver as a container launcher.
  • Archon: a review pass on a different model family than the build agent; one Postgres with two databases or two instances (backup scope).
  • GitHub: rulesets requiring a status from a specific identity, and whether that identity must be a GitHub App; API rate budget for a 60 s poll.

06Decisions deferred to the deploy gate

Both are deferred, with the rest of the register in the guide §4. The recommendations below are input for that gate.

D-9 · Core pair on one host. Recommended: Paperclip + Archon (§00, §03). Keep Multica + Archon if a second host is likely. Choosing Paperclip changes the Design doc's dispatcher, the guide's Phase 2 and the "who enforces what" section, nothing else.

D-8 · How local loops learn about GitHub events. Recommended: the local 60 s poller. All logic stays local and there's no inbound path. Alternatives: a self-hosted Actions runner as a pure event relay (needs a workflow file per repo and Linux with sudo), or webhooks through a tunnel (rejected: an inbound path into the agent side).
