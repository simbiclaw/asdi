00Thesis

  • You manage outcomes, not runs. You admit work, make the calls only you can make, review judgment-class changes and gate exposure. Agents decide how to build.
  • Only seven rules are hard (§02). Everything else is a request the agent can override with a reason. Extra process is the new micromanagement.
  • Failures are caught inside the loop that made them. The nested loops L0–L4 plus the production loop (§03) catch most failures before you would.
  • A claim is not a result (C-5). A run is green only when verification that ASDI runs itself passes. The agent's own report never counts (§13).
  • Design happens by shipping. Features enter as experiment cards and ship behind default-off flags. The metric and your preview of the running thing decide what's kept, not a spec reviewed in committee.

02Seven hard rules; everything else is a request

Hard rules: the platform enforces them

  1. Merge authority by change class. Only the merge bot merges, after CI, the review passes and the asdi/policy class check are green on the PR head. The same checks run again on main after the merge, and a failure auto-reverts. Judgment-class changes also need you (GitHub ruleset + CODEOWNERS). Agent tokens can't merge.
  2. done_check. A run can't finish red, and green means ASDI's verifier passed, not the agent's own run (C-5). The agent CLI's own stop hook where it has one (Claude Code, Codex); the launcher's verifier for every agent CLI.
  3. Sandbox. Container and network per run, egress allowlist, push to its own branch only, no network route to production.
  4. Secrets outside the sandbox. Tokens, the model key included, are injected at egress; production secrets exist only in containers on the prod network.
  5. Guardrails. Turn, spend and wall-clock limits per run.
  6. No irreversible actions by agents. Exposure ramps, migrations on shared data, external side effects, pricing and force-pushes are yours. Every production migration needs a verified snapshot taken just before it.
  7. Protected paths. Generated and vendored code is never edited; changes to tests, CI, verify/, evals/ or .asdi/ are allowed but always flagged. A product PR may add a feature file; it can't edit existing verification files.

Requests: the agent may override with a reason

  • Conventions, style, architecture preferences (AGENTS.md; CLAUDE.md is a one-line import of it)
  • Whether to plan, and how much
  • Order of work, step size, tools
  • Asking for review mid-run
  • Skills for repeated workflows
  • Commit granularity and PR structure within the diff budget
  • Note files such as ASSUMPTIONS.md; set-aside requests go in OVERRIDES.md with the reason
  • Engineering principles: prove on the real artifact, root cause first, verifiable units, test behaviour
  • A decision log on long runs

A request ignored twice despite emphasis is promoted only if it's truly must-always or must-never. A rule that turns out to be a preference is demoted. Every model release triggers a review of the whole list.

03Loops: catch failures inside the run

04System architecture

  • Reset, not retry. Two strikes (a failed check or a repeated PR comment) and the lead agent writes brief v2 from the lessons and starts a fresh session. A failed reset reaches you only if a decision blocks it; otherwise the task is dropped and reported weekly.
  • Compounding. The same correction seen twice is fixed at the highest layer that works: codebase, check, test, and text last. Text changes need a skill eval. A retirement eval removes rules that no longer change outcomes.
  • Production-first admission. Agents and products share one machine, so this is the main protection for users: the dispatcher lowers agent concurrency when the SLO error budget burns, prod containers are under memory pressure, or the reserved model instance queues. Agent work can be preempted; production can't.

06Deploy profile P-1: self-hosted on the Mac Studio

Layout

  • Mac Studio M3 Ultra 256 GB is the only host. Prod zone: containers on the prod network, with CPU and memory limits and OOM priority. Agent zone: the agent, staging and ops networks, plus one network per run, capped below that reserve. vllm-mlx on the host, with an instance reserved for products.
  • Ingress: outbound tunnel; blue/green proxy with weighted canary.
  • Release: local CI builds and signs images into the local registry; the prod deployer pulls them. Nothing pushes into prod.
  • Outside the house: external probe with push alerts; encrypted offsite backups; monthly restore drill.

macOS operating rules

  • FileVault blocks boot after power loss until you type the password: UPS, plus authenticated restart for planned reboots.
  • No sleep and no automatic updates on the Studio. An OS update now stops production, agents and monitoring together, so it happens in announced windows.
  • Memory capped per Docker container, so the split is deliberate, not contention.
  • Disk janitor for images, logs and snapshots; separate volumes per role.

08Who enforces what

Multica holds the board, squads and runtimes, with its daemon on the agent network on the Studio. Archon runs the pipelines around outcomes: PR gate, the four review passes, the asdi/policy check with its coverage gate, packet assembly, the fix loop (max 2), triage, readouts, the flag janitor, verification and drift sweeps, compounding, the skill-eval gate, the seeded-defect suite and the TRM ledger. A local Archon poller reads GitHub every 60 s and posts statuses (D-8). GitHub is passive: code, PR UI, rulesets, CODEOWNERS. No GitHub Actions, no webhooks.

Three identities with separate rights: Archon can only post statuses; the merge bot can only merge PRs whose required checks are green; agents can only push branches and open PRs.

Launcher (ASDI-owned) is the only caller of the Docker socket proxy. It creates the network, services and container for each run, enforces guardrails from outside, runs static gates and the verifier, exports evidence for signing, and pauses or resumes runs. Probe runner and rollback controller sit on the ops and prod networks and run no model.

09Your surface

Five touchpoints

  1. Admit work within a WIP limit: features as experiment cards; maintenance under standing charters you approve once.
  2. Decide escalations: product calls, security boundaries, competing priorities, anything irreversible. For design forks the metric decides; you break ties.
  3. Review judgment-class PRs as if you'll be paged.
  4. Gate exposure: preview, ramp, keep or kill; approve migrations, external side effects, pricing.
  5. Run the weekly system loop: metrics, TRM moves, rule retirement, experiment verdicts, flag debt.

You stop doing

  • Approving plans at T1+, or specs for features
  • Approving deploys
  • Finding production bugs yourself
  • Pre-merge review of reversible, in-charter PRs
  • Watching runs outside probation; re-prompting by hand
  • Triaging mechanical failures; slicing the work
  • Writing ALL-CAPS rules or hooks for preferences
  • Polling dashboards; counting lines or AI share

13Verification subsystem

C-5: the agent's claim of success never counts. Only a result produced by verification that ASDI runs itself does. pstack and gstack define what a meaningful check is but enforce nothing; ASDI enforced that a check passed but not what it meant. This section joins the two.

Where each capability lives

A capability is ASDI-native if a failure must be blocked, if it needs authority or reach the agent must not have, if its result must be independent of the agent, or if it must outlive a run. Knowledge about one product goes in that product's harness. The rest are requests.

TierHolds

Harness (product repo, verify/ and .asdi/)Verify skill, feature map, negative controls, drive fixtures, read-only production probes, static-gate manifest, rule registry, seeded defects
Request (AGENTS.md)Engineering principles, decision log, test-first where cheap

Harness contract

  • Verify skill: one executable with launch, doctor, drive, control, cleanup. No model needed to run it.
  • Feature map: one file per user-facing feature: the paths it owns, how to reach and drive it, the proof, a negative control, an optional production probe.
  • Statuses: pass, fail, blocked, error or not applicable. Only pass satisfies a gate. Every proof compares an observed value with a literal expected one.
  • Limits: each proof states what it does not cover.
  • Self-test: the proof passes and its negative control is caught, or the harness is unusable.

Merge and post-merge check

One rule: test what is on main, and deploy only what passed there.

  1. The gate runs on the PR head. The ruleset requires ci, asdi/policy and an up-to-date branch. A new head commit invalidates earlier evidence and verdicts.
  2. The merge bot merges directly (you do, until agent merges are on).
  3. ASDI runs static gates and the verifier on the commit that landed on main.
  4. Fail: an auto-revert PR opens and the release stops. Pass: CI builds from that commit and the deployer deploys it.

No merge queue. It tests a temporary commit with its own ID, which adds a second place to post statuses and its own timeouts. That pays off only when many PRs merge in parallel, which a WIP limit of 3 does not produce.

Left out on purpose: a router skill that scripts the agent, any playbook where the agent lands its own stack, human approval gates at T1+, a browser using your logged-in sessions, and installing either pack as a dependency.
